# معماری فنی و قرارداد لایه‌ها

مرجع توسعه‌دهنده. سند حاکم `101` می‌گوید محصول چیست؛ این‌جا می‌گوید کد چطور
چیده شده و هر لایه حق دارد به چه چیزی دست بزند.

---

## ۱) پنج لایه و مرزشان

```
┌─ ۱ ورودی و دارایی ──────────────────────────────────────┐
│  متن، فایل، عکس، کلیپ → Asset                            │
│  می‌داند: چطور فایل بگیرد و شناسنامه‌دار کند              │
│  نمی‌داند: محتوا برای چیست                                │
└──────────────────────────┬──────────────────────────────┘
                           ↓ Asset
┌─ ۲ فهم و پلان ──────────────────────────────────────────┐
│  ProductionType + attributes + material + duration       │
│  → Project → Sequence → Shot → SceneDirection            │
│  می‌داند: چطور از ایده شات‌لیست بسازد                    │
│  نمی‌داند: کدام مدل، چقدر هزینه                          │
└──────────────────────────┬──────────────────────────────┘
                           ↓ PlanStep
┌─ ۳ ارکستراسیون ─────────────────────────────────────────┐
│  AiModel router · Job queue · Wallet hold/settle/release │
│  می‌داند: چه کسی ارزان‌تر و در دسترس‌تر است               │
│  نمی‌داند: خروجی قرار است تبلیغ باشد یا مستند            │
└──────────────────────────┬──────────────────────────────┘
                           ↓ Generation
┌─ ۴ مونتاژ و پرداخت ─────────────────────────────────────┐
│  چسباندن نماها · صدا · موسیقی · زیرنویس · واترمارک       │
│  می‌داند: چطور نماها را به یک فایل تبدیل کند             │
│  نمی‌داند: فایل کجا منتشر می‌شود                          │
└──────────────────────────┬──────────────────────────────┘
                           ↓ Asset (final_output)
┌─ ۵ انتشار ──────────────────────────────────────────────┐
│  Publication per target · license gate                   │
│  می‌داند: هر مقصد چه می‌خواهد و چه مجوزی لازم دارد        │
└─────────────────────────────────────────────────────────┘
```

**قاعده مرز:** هر لایه فقط با موجودیت مرزی لایه بالادستش حرف می‌زند. لایه ۳
هرگز `ProductionType` نمی‌خواند و لایه ۲ هرگز `AiModel` نمی‌بیند. هر بار که
یک لایه به دو لایه بالاتر دست بزند، همان جایی است که تغییر بعدی می‌شکند.

## ۲) ماژول‌ها و مسئولیتشان

| ماژول | لایه | مسئول | نباید بداند |
|---|---|---|---|
| `registry` | — | نوع تولید، سطح خدمت، مجوز، کاتالوگ | هیچ پروژه‌ای |
| `assets` | ۱ | آپلود و شناسنامه دارایی | معنی محتوا |
| `projects` | ۲ | ایده → شات‌لیست → کارگردانی نما | نام مدل، قیمت |
| `ai-gateway` | ۳ | رجیستری مدل، روتر، failover | نوع تولید |
| `jobs` | ۳ | صف کار و پاکت بودجه | چه چیزی تولید می‌شود |
| `wallet` | ۳ | رزرو، تسویه، آزادسازی، دفتر | چرا خرج شد |
| `compliance` | ۲ و ۵ | قوانین، تعهد، دروازه بازبینی | جزئیات تولید |
| `publications` | ۵ | نمایش در هر مقصد | چطور ساخته شد |

`registry` عمدا لایه ندارد: **تنها منبع حقیقت مشترک** است و همه از آن
می‌خوانند. اگر فرم استودیو فهرست خودش را داشته باشد و پنل راهبر فهرست
دیگری، روزی که نوعی اضافه شود یکی‌شان فراموش می‌شود.

## ۳) هفت تصمیم ساختاری و دلیلشان

**۱ · نوع تولید ردیف داده است، نه enum.**
`ProductionType.fieldSchema` می‌گوید فرم بعد از انتخاب نوع چه می‌پرسد. افزودن
نوع تازه یا فیلد تازه هیچ مهاجرتی نمی‌خواهد. اثبات: بند ۵ آزمون
`registry.check.ts`.

**۲ · زیرشاخه‌ها در ستون Json، با اعتبارسنجی در سرویس.**
شکل این داده به نوع وابسته است، پس هیچ ستون ثابتی نمی‌تواند اعتبارش را
تضمین کند. `RegistryService.validateAttributes` سخت‌گیرانه بررسی می‌کند و
**فیلد ناشناخته را دور می‌ریزد** تا داده بی‌صاحب تلنبار نشود.

**۳ · سطح خدمت با سیاست تعریف می‌شود، نه با فهرست شناسه مدل.**
«مدل‌های اقتصادی» یعنی `maxCostPerUnit`، نه ده شناسه که با افزودن مدل یازدهم
کهنه می‌شود. نتیجه: رجیستری مدل و سطوح خدمت مستقل می‌مانند و افزودن مدل تازه
هیچ سطحی را نمی‌شکند.

**۴ · قیمت سطوح `null` است.**
عمدی. تا هزینه واقعی یک ثانیه ویدیو اندازه‌گیری نشود، هر عددی حدس است. بذر
هرگز `priceIrt` را نمی‌نویسد؛ فقط پنل راهبر می‌تواند پرش کند.

**۵ · کارگردانی نما مبدأ هر فیلد را نگه می‌دارد.**
`SceneDirection.origins` برای هر فیلد می‌گوید `USER` است یا `MACHINE`. با
اولین ویرایش کاربر، همان فیلد به `USER` تغییر می‌کند. دو فایده: کاربر می‌بیند
ماشین چه اضافه کرده، و بعدا می‌شود سنجید کدام پیشنهادها پذیرفته شدند.

**۶ · مجوز رسانه مقصد انتشار را می‌داند.**
`MediaLicense.allowedTargets` خالی یعنی همه مقصدها؛ پر یعنی فقط همان‌ها. پس
ترک غیرتجاری برای دانلود دیده می‌شود ولی در فهرست انتخاب برای انتشار روی فلک
اصلا نمی‌آید. این‌جا جای «قوانین رایگان» در کد است.

**۷ · یک اثر، چند رکورد نمایش.**
`Publication` با کلید یکتای (پروژه، مقصد). فایل یک بار ساخته و یک جا نگه
داشته می‌شود؛ برداشتن اثر از پنل راهبر یک `UPDATE` است، نه شکار در چند سامانه.

## ۴) قواعد کدنویسی که با گرپ قابل بررسی‌اند

```bash
# هیچ نام مدلی در کد ثابت نباشد — مدل ردیف داده است
grep -rniE "gpt-|claude-|gemini|veo|runway|kling" apps/api/src --include='*.ts'

# هیچ کرونی داخل پروسه API — تیک از بیرون می‌آید.
# الگو عمدا به «کاربرد» محدود است نه هر جای متن، وگرنه خودِ توضیح‌هایی که
# می‌گویند «کرون نداریم» هشدار کاذب می‌سازند.
grep -rnE "^\s*@Cron\(" apps/api/src packages --include='*.ts'

# هیچ ارجاعی به پایگاه داده پروژه همسایه
grep -rni "webcasting" apps/api/src --include='*.ts'

# قرارداد نام‌گذاری کد دلیل: فقط snake_case
psql -c "SELECT code FROM \"ReasonCode\" WHERE code ~ '[A-Z]'"
```

هر چهار تا باید خالی برگردند.

## ۵) نکته‌های عملیاتی

- **پورت لوکال API برابر `3250` است** (`3200` به ماژول دیگری روی همین ماشین
  داده شده). روی سرور همچنان `3200` است و `docker-compose.prod.yml` دست‌نخورده.
- **بذر داده:** `node dist/seed-registry.js` — بی‌اثر در تکرار. `isActive` نوع
  تولید و `priceIrt` سطح خدمت را **به‌روزرسانی نمی‌کند**، تا اجرای دوباره
  تصمیم مالک را برنگرداند.
- **آزمون‌ها:** `test/wallet-ledger.check.ts` و `test/registry.check.ts`. باید
  با `tsc --outDir` **داخل `apps/api`** کامپایل شوند، وگرنه `@nestjs/core`
  پیدا نمی‌شود.
- **مهاجرت روی سرور:** `prisma db push` روی جدول‌های تازه بی‌خطر است (همه
  ستون‌های تازه یا اختیاری‌اند یا پیش‌فرض دارند). `Project.goal` و
  `Project.tone` اختیاری شدند و برای ردیف‌های دوره اول می‌مانند.
